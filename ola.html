I. Análisis y Selección de Patrones

1. ¿Qué patrón de diseño utilizaría para manejar las diferentes formas de calcular el costo del envío?
STRATEGY Justificación: El costo de envío cambia dinámicamente según el contexto (Estándar, Express, Nocturna, Lluvia). El patrón Strategy permite encapsular cada algoritmo de cálculo en su propia clase bajo una interfaz común (`IEnvioStrategy`). Esto elimina la necesidad de tener múltiples sentencias `if/else` o `switch` en la clase principal del pedido, respetando el principio Open/Closed (se pueden agregar nuevas lógicas de envío en el futuro sin modificar el código existente).
2. ¿Qué patrón de diseño utilizaría para notificar automáticamente a los diferentes componentes?
OBSERVER Justificación: Existe una dependencia de uno-a-muchos entre el estado del pedido y los componentes interesados (Cliente, Restaurante, Domiciliario, Facturación). El patrón Observer permite que el objeto "Pedido" actúe como un Sujeto (Publisher) que mantiene una lista de suscriptores. Al cambiar su estado, itera sobre la lista y ejecuta un método `update()` en cada uno, logrando un bajo acoplamiento (el pedido no necesita conocer la lógica interna de la facturación o del restaurante).
3. ¿Qué patrón de diseño utilizaría para manejar las diferentes formas de aplicar descuentos?
DECORATOR Justificación: Aunque Strategy serviría si solo se aplica un descuento único, Decorator es superior en este escenario comercial. Permite "apilar" o acumular descuentos de forma dinámica en tiempo de ejecución (por ejemplo, aplicar descuento de cliente frecuente y, sobre ese resultado, aplicar un código promocional). Envuelve el objeto base de cálculo en capas sucesivas que modifican el costo final sin alterar la estructura base.
4. ¿Qué patrón de diseño utilizaría para crear los diferentes tipos de reportes?
FACTORY METHOD Justificación: Permite centralizar la lógica de instanciación de los reportes (PDF, Excel, JSON). El código principal solo solicita "crear reporte tipo X" a una clase Fábrica (`ReporteFactory`), la cual devuelve una instancia que cumple con la interfaz `IReporte`. Así, el código cliente no se acopla a las clases concretas (`ReportePDF`, etc.) y es trivial añadir nuevos formatos de exportación.

Explicación de la Estructura de Clases

El sistema utiliza una arquitectura orientada a eventos e inyección de dependencias para calcular y auditar pedidos:

  • Pedido (Núcleo): Mantiene el estado, productos y delega el cálculo final y notificaciones.
  • Estrategias de Envío: Implementan IEnvioStrategy para calcular el flete dinámicamente.
  • Decoradores de Costo: Envuelven a ICalculadorPrecio para apilar descuentos de forma recursiva.
  • Observadores del Estado: Implementan IObserver para reaccionar asincrónicamente a los cambios de estado.
  • Factory de Reportes: Centraliza la instanciación de formatos de reporte a partir de la interfaz IReporte.
